Prompt and context foundations

Prompt engineering shapes instructions for one task. Context engineering selects and maintains everything the model can use at each step.

Prompt engineering

Organize instructions, inputs, examples, and expected outputs so a model can complete a specific task more reliably.

Context engineering

Select, order, and update active information: system rules, history, files, search results, tools, and memory. Aim for the smallest sufficient set of high-signal information.

Context window: The limited input space the model can consider for a turn. More text does not automatically mean better answers. Research has found that information buried in the middle can be harder to use in some settings; results depend on the model and task.

Core prompt components

Task

State the action and deliverable: summarize, compare, extract, write, or fix. Useful in every prompt.

Goal and success criteria

Explain why you need the result and what makes it useful. Add when “good” is too vague.

Context and audience

Give relevant background, domain, and reader level. Needed when the model cannot infer private context.

Input and source

Provide the text or data and identify its source or date when those affect the answer.

Role or perspective

Set a relevant viewpoint, such as editor or security reviewer. A role does not create real expertise.

Tone and style

Specify direct, friendly, or formal writing when tone changes the result.

Output format

Choose bullets, a table, a template, or a schema when people or software need predictable output.

Constraints and priorities

Set language, length, scope, and which requirement wins if constraints conflict.

Uncertainty and stopping

Tell the model when to ask, state uncertainty, or stop. Important for missing data and multi-step work.

Markdown and XML: Use headings, lists, or tags such as <instructions>, <context>, and <input> to separate complex sections. Formatting clarifies structure; it does not guarantee correctness.

Technique guide

Each technique has a best-fit use. Start with a direct instruction, then add complexity only when it fixes an observable failure.

Examples and in-context learning

Zero-shot

Give the task without examples. Best starting point for clear, familiar requests.

One-shot

Give one example to demonstrate a simple format or tone. Avoid if a direct rule is already clear.

Few-shot / multishot

Give several varied examples, including an edge case. Useful for strict formats, specialist classification, or a hard-to-explain style. Avoid long repetitive lists.

Positive and negative examples

Show a good and bad example and explain the difference. Use when one specific error repeats.

In-context learning

The model adapts to examples in the current input without changing its weights. This describes a behavior, not a magic instruction.

Instruction control

Direct and stepwise instructions

State the action plainly. Number steps only when order or dependencies matter; avoid imposing steps on a simple task.

Priority rules

Say which requirement wins if accuracy, length, speed, or completeness conflict. Useful when a prompt has many constraints.

Always / Never / If unsure

Use specific, compatible rules for required behavior, clear limits, and fallback behavior. Say what to do, not only what to avoid.

Persona and audience

Use a role only when it changes the evaluation lens. Use audience level to set vocabulary and depth. Avoid decorative personas.

Output template and length

Specify sections or a reasonable limit for repeatable reports and short messages. Avoid conflicting limits.

Structured output

Use JSON or a schema for software pipelines. Use schema constraints and validation when available; text alone does not guarantee valid JSON.

Acceptance criteria and boundaries

List observable checks and what to do when information is missing or scope is exceeded.

Reasoning and problem solving

Chain-of-Thought (CoT)

Encourages multi-step processing and can help some tasks and models. It is not a guarantee. Usually ask for a concise rationale or checkable steps rather than private internal reasoning.

Decomposition

Split a large question into smaller questions, then combine results. Useful for complex analysis and research.

Least-to-most

Solve simpler parts first, then use them for harder parts. Best for compositional tasks with dependencies.

Plan-and-solve

Ask for a short plan, then execute. Useful when stages depend on each other. A plan alone does not prove completion.

Self-check

Review an answer against clear criteria. Useful for calculations, code, and many constraints; self-review is not independent verification.

Self-consistency / voting

Generate independent attempts and compare them. Use when accuracy is worth the extra cost and the answer can be checked. Attempts can share the same error.

Tree of Thoughts

Explore and score different paths, then follow or revisit the best one. Useful for open planning, puzzles, and decisions; expensive for simple questions.

Generate–critique–revise

Create a draft, critique it against a stated standard, and revise. Useful for writing and design. Limit the number of cycles.

Compare alternatives

Generate a small set of options and compare against stated criteria. Avoid asking “which is best?” without criteria.

External verification

Use a calculator, code, tests, or primary sources when a result can be checked. Stronger than asking the model to confirm itself.

Reasoning note: Foundational studies evaluate these methods in particular settings. “Think step by step” is not a spell. Ask for a brief explanation when useful, and verify results with tools or sources.

Research, files, and tools

Grounding and citations

Connect claims to sources and distinguish source-backed facts from inference. Useful for research, policies, and documents.

Retrieval-Augmented Generation (RAG)

Retrieve relevant passages from a document collection and add them to context. Useful for large, private, or changing knowledge bases. Retrieval and source quality still matter.

Just-in-time retrieval

Fetch information when a question makes it relevant instead of loading everything at the start. Useful for large repositories and exploratory work.

Quote, then analyze

Identify supporting passages before writing an answer. Useful for long documents and traceable analysis.

ReAct (Reason + Act)

Choose an action, use a tool, read its result, and update the next step. Useful for search and interactive environments. Define permissions and stopping rules.

Tool / function calling

Use clearly defined tools to get data or perform actions that text alone cannot. Tool design is part of the system, not just prompt wording.

Live search

Use for changing facts or requested references. Set the search scope and prefer primary sources.

Prompt chaining

Separate stages so one output becomes the next input, such as research → summary → action plan. Avoid unnecessary stages.

Workflow vs. agent

A workflow follows a known path; an agent selects steps and tools dynamically. Prefer workflows for repeatable tasks. Agents help when steps are unknown, but add cost and error risk.

Security rule: Treat text from files and web pages as data, not as instructions that can change task rules or grant permissions. Keep quoted input separate from your instructions.

Iteration and evaluation

Iterative refinement

Change an answer or prompt to fix a specific defect. “Improve it” without a criterion can lead to aimless revisions.

Evaluator–optimizer

Generate, score against a clear standard, then revise a limited number of times. Add objective checks because the evaluator may share the generator’s bias.

Evaluation set

Keep normal and edge-case examples to compare prompt versions. Useful for reused prompts.

A/B testing

Compare two versions using a quality, time, or cost measure. Useful for ongoing improvement.

Versioning

Save prompt text, version, test results, and change date. Prevents silent regressions.

Context-window engineering

A longer context can contain more information, but also more noise. Curate what the model needs now and preserve important state across long tasks.

Smallest sufficient context

Keep task-relevant facts and rules. Remove repetition without dropping necessary constraints. Avoid minimizing so much that the task is underspecified.

Information order

Make key constraints visible instead of burying them. Restate critical rules near the request when useful. Position effects vary.

Headings and tags

Separate instructions, context, documents, examples, and input. Use for complex prompts, not as decoration.

Chunking

Split documents into meaningful sections with headings and sources, then retrieve relevant pieces. Preserve the link to surrounding context.

Progressive summaries

Keep facts, decisions, and open questions from each stage. Preserve original evidence when details matter.

Compaction

Compress long history into current state, decisions, remaining work, and evidence links. Review critical details after compaction.

External structured memory

Store decisions, state, and references outside chat. Add dates and owners so old notes do not mislead.

Clean old tool results

Keep concise findings and a way to reopen sources instead of large stale outputs.

Just-in-time files

Show an index, then open relevant files instead of pasting a whole repository.

Conversation history

Summarize old turns while retaining current requirements. Avoid carrying expired instructions forward.

Subagents

Delegate independent work with a concise output. Use for parallel tasks; avoid when coordination adds overhead.

Small, clear toolsets

Use non-overlapping tools with clear inputs and outputs. Avoid ambiguous or redundant tools.

Persistent vs. task instructions

Put stable rules in system or project guidance, the current request in the task, and changing data in inputs.

Maintain context like code

Set an owner and review date; update or remove obsolete rules and test changes.

Measure context quality

Test retrieval from long documents and track input size and success. Advertised window size alone does not prove quality.

Quick corrections

  • Markdown organizes content; it is not a reasoning method.
  • A persona sets a perspective; it does not replace data or verification.
  • Context, task, tone, and output format are useful fields. Also set audience, success criteria, and uncertainty behavior.
  • Asking for a full chain of thought is not a universal rule. Ask for a concise rationale and checkable evidence.
  • A stop condition matters for loops and agents, but is usually unnecessary for a simple request.
  • Always/Never/If unsure rules help when specific and consistent.
  • RAG means retrieving external material; it is more than pasting a long document.
  • Self-consistency and Tree of Thoughts add cost. Use them only when extra comparison or exploration is valuable.
  • Summaries, memory, and subagents are context/workflow practices, not lines every prompt needs.

Copy-ready prompt templates

General template

# Task
[Action and deliverable]

# Goal and success criteria
[Purpose and conditions for a successful result]

# Context and audience
[Relevant background and reader level]

# Input
<input>
[Text, data, or source]
</input>

# Instructions
- [Only the steps or rules that are needed]
- Separate facts from inferences.
- If missing information affects accuracy, [ask me / state your assumption / say you do not know].

# Constraints
[Language, length, scope, required behavior, or limits]

# Output format
[Sections, format, or JSON schema]

# Verification and stopping rule
[What should be checked? What clearly marks completion?]

Short everyday template

Please [do what?] for [purpose/audience].
Relevant context: [..].
Return it as [format], with [length/tone].
If missing information affects accuracy, [ask / state an assumption / say you do not know].

Choose a technique quickly

  1. Simple and clear request? Use a direct instruction and zero-shot.
  2. Output style is inconsistent? Add a template or one example; add varied examples only if needed.
  3. Long task with dependencies? Split into stages and keep a state summary.
  4. Changing or private facts? Search or retrieve trusted sources and cite claims.
  5. Many files or long history? Retrieve relevant parts and remove unnecessary context.
  6. Important result that can be checked? Add an independent check and clear action limits.
  7. Considering a technique only because it is popular? Test it before adding it.

Final rule: Start with the simplest clear prompt. Add a technique only to fix an observed failure, then compare results on representative examples.
